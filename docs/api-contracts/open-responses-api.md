# DSS over the Responses API

**Status:** Evaluated, not adopted. **Date:** 2026-08-31.

How the DSS *could* offer an OpenAI Responses-compatible API, and what it would cost.

**Nobody has asked for this.** The DSS runs in a private subnet and is called only by our own
channel services — no browser, no third-party SDK. This document exists so the cost is known
if someone asks again. §7 has the recommendation.

Read with `api-contract.md`, the DSS-native API. That stays the internal one.

Checked against the OpenAI OpenAPI spec, August 2026.

---

## 1. What fits and what does not

| DSS thing | Responses has it? | How |
|---|---|---|
| Streaming an answer | Yes | `response.output_text.delta` |
| **Sources per sentence** | **Yes** | `annotations` — `url`, `title`, and the text span |
| **Refusal** | **Yes** | `refusal` content type, with its own stream events |
| History | Yes | `input` as a list of messages |
| Image input | Yes | `input_image` in a message — but see §6 for the security cost |
| Our `cause` codes | No | `error.code` is a fixed list. Ours are not in it. |
| `no_match`, `needs_clarification` | No | No status means "found nothing" or "need more" |
| Channel (voice, SMS) | No | No field |
| `region` / `area` / geometry | No | No location field |

### Sources are native

Every cited sentence can carry a real citation:

```jsonc
{
  "type": "url_citation",
  "url": "https://agmarknet.gov.in/...",
  "title": "Agmarknet",
  "start_index": 0,
  "end_index": 61
}
```

`file_citation` does the same for documents. **But `start_index` is a character offset, and
which unit it counts is the single most dangerous detail in this document — see §5.2.**

### The `metadata` limit

`metadata` holds **16 keys. Values are strings, 512 characters.** No lists, no nesting, no
numbers.

This is OpenAI's platform-wide convention, not a Responses rule — one shared schema used in 41
places across their spec. We could allow more. But the moment our `metadata` behaves
differently, we are no longer compatible, which removes the reason to use the format at all.

## 2. Endpoints

| What | Path | Works? |
|---|---|---|
| Create a response | `POST /v1/responses` | Yes |
| Get one back | `GET /v1/responses/{id}` | **No — `404`** |
| Cancel | `POST /v1/responses/{id}/cancel` | **No — `404`** |
| Delete | `DELETE /v1/responses/{id}` | **No — `404`** |

Three of four do not work because the DSS stores nothing.

## 3. Request

### Fields

| DSS field | Responses | Keys |
|---|---|:--:|
| `query` | `input` | — |
| `history` | `input` as a list of messages | — |
| `source_lang`, `target_lang` | `metadata.oan_source_lang` / `oan_target_lang` | 2 |
| `channel` | `metadata.oan_channel` | 1 |
| `subject_ref` | `oan_user_id`, `oan_subject_ref`, `oan_ref_issuer`, `oan_ref_expires` — **four keys**, because `metadata` cannot nest | 4 |
| `location.region` / `area` | `metadata.oan_region` / `oan_area` | 2 |
| `location.geometry` | `metadata.oan_geo` — `"lon,lat"` as a string. A polygon cannot travel. | 1 |
| `X-Session-Id` | `metadata.oan_session_id` | 1 |
| `X-Trace-Id` | `metadata.oan_trace_id`, or the DSS makes one | 1 |
| `request_options.response_max_chars` | `metadata.oan_max_chars` — **not** `max_output_tokens`, which counts tokens | 1 |
| `request_options.modality` | Not sent. An `input_image` part says it. | 0 |

**Fourteen of sixteen keys used. Two left.** `subject_ref` alone costs four.

### History

`input` takes a plain string or a list of messages:

```jsonc
"input": [
  { "role": "user",      "content": "What is the mandi price of wheat?" },
  { "role": "assistant", "content": "Wheat is ₹2,275 per quintal at Anand mandi." },
  { "role": "user",      "content": "And potato?" }
]
```

Not a workaround. The spec says a message with `role: "assistant"` is *"presumed to have been
generated by the model in previous interactions"*, and names stateless multi-turn as supported.

**Only `user` and `assistant` are accepted.** `system` and `developer` are rejected — see §6.2.

The caller sends the whole conversation every turn. The three deployments already do that.

### Fields the DSS ignores on input

`temperature`, `top_p`, `instructions`, `tools`, `tool_choice`, `parallel_tool_calls`,
`reasoning`, `text.format`, `service_tier`, `truncation`, `max_output_tokens`.

Accepted and ignored, not rejected, because SDKs send several by default.

**Ignored on input does not mean absent from output.** The `Response` object requires most of
them back — see §4.1.

`model` is required by the SDK and selects nothing. Any value is accepted.

`store` must be `false`. `true` returns `400`.

### 4.1 A simple question, not streaming

First turn, so `input` is a plain string.

**Request**

```jsonc
POST /v1/responses
{
  "model":  "oan-dss",
  "input":  "What is the mandi price of wheat this week?",
  "stream": false,
  "store":  false,
  "metadata": {
    "oan_session_id":  "sess_8f3a1c",
    "oan_trace_id":    "trc_9f2b7c1a",

    "oan_source_lang": "hi",
    "oan_target_lang": "hi",
    "oan_channel":     "web",

    "oan_user_id":     "usr_9921",                 // subject_ref.user_id
    "oan_subject_ref": "prov_opaque_7b2f...e0",    // subject_ref.ref
    "oan_ref_issuer":  "experience",               // subject_ref.issuer
    "oan_ref_expires": "2026-09-01T18:30:00Z",     // subject_ref.expires_at

    "oan_region":      "IN-GJ",
    "oan_area":        "Anand",
    "oan_geo":         "72.93,22.56",

    "oan_max_chars":   "1200"
  }
}
```

**Response — every required field.**

The spec's `Response` schema requires fourteen: `id`, `object`, `created_at`, `error`,
`incomplete_details`, `instructions`, `model`, `tools`, `output`, `parallel_tool_calls`,
`metadata`, `tool_choice`, `temperature`, `top_p`.

So the DSS must **echo back fields it ignored on the way in**. A strict typed SDK (Go, Java,
C#, Python with `model_validate`) raises if any are missing.

```jsonc
{
  "id":                  "resp_9f2b7c1a",
  "object":              "response",
  "created_at":          1788105600,
  "status":              "completed",
  "error":               null,
  "incomplete_details":  null,

  "instructions":        null,        // ignored on input, required on output
  "model":               "oan-dss",
  "tools":               [],
  "tool_choice":         "auto",
  "parallel_tool_calls": false,
  "temperature":         1,
  "top_p":               1,
  "usage":               null,        // the DSS does not count tokens — see §7.4

  "output": [
    {
      "id":      "msg_1",
      "type":    "message",
      "role":    "assistant",
      "status":  "completed",
      "content": [
        {
          "type": "output_text",
          "text": "इस सप्ताह आनंद मंडी में गेहूं का भाव ₹2,275 प्रति क्विंटल है।",
          "annotations": [
            { "type": "url_citation", "url": "https://agmarknet.gov.in/...",
              "title": "Agmarknet", "start_index": 0, "end_index": 61 }
          ],
          "logprobs": []
        }
      ]
    }
  ],

  "metadata": { "oan_trace_id": "trc_9f2b7c1a", "oan_status": "answered" }
}
```

`end_index: 61` is **Unicode code points** — see §5.2. That sentence is 61 code points and 151
UTF-8 bytes.

**Later examples show only `status`, `output`, `error`, and `metadata`.** The eleven constant
fields above are present on every real response.

### 4.2 The same question, streaming

`"stream": true`. **The full event sequence** — a client that builds state from
`output_item.added` needs every one of these.

```
event: response.created
data: {"type":"response.created","response":{"id":"resp_9f2b","object":"response","status":"in_progress","created_at":1788105600,"error":null,"incomplete_details":null,"instructions":null,"model":"oan-dss","tools":[],"tool_choice":"auto","parallel_tool_calls":false,"temperature":1,"top_p":1,"output":[],"metadata":{"oan_trace_id":"trc_9f2b7c1a"}},"sequence_number":0}

event: response.in_progress
data: {"type":"response.in_progress","response":{"id":"resp_9f2b","status":"in_progress"},"sequence_number":1}

event: response.output_item.added
data: {"type":"response.output_item.added","output_index":0,"item":{"id":"msg_1","type":"message","role":"assistant","status":"in_progress","content":[]},"sequence_number":2}

event: response.content_part.added
data: {"type":"response.content_part.added","item_id":"msg_1","output_index":0,"content_index":0,"part":{"type":"output_text","text":"","annotations":[],"logprobs":[]},"sequence_number":3}

event: response.output_text.delta
data: {"type":"response.output_text.delta","item_id":"msg_1","output_index":0,"content_index":0,"delta":"इस सप्ताह आनंद मंडी में गेहूं का भाव ₹2,275 प्रति क्विंटल है।","logprobs":[],"sequence_number":4}

event: response.output_text.annotation.added
data: {"type":"response.output_text.annotation.added","item_id":"msg_1","output_index":0,"content_index":0,"annotation_index":0,"annotation":{"type":"url_citation","url":"https://agmarknet.gov.in/...","title":"Agmarknet","start_index":0,"end_index":61},"sequence_number":5}

event: response.output_text.done
data: {"type":"response.output_text.done","item_id":"msg_1","output_index":0,"content_index":0,"text":"इस सप्ताह आनंद मंडी में गेहूं का भाव ₹2,275 प्रति क्विंटल है।","logprobs":[],"sequence_number":6}

event: response.content_part.done
data: {"type":"response.content_part.done","item_id":"msg_1","output_index":0,"content_index":0,"part":{"type":"output_text","text":"इस सप्ताह…","annotations":[{"type":"url_citation","url":"https://agmarknet.gov.in/...","title":"Agmarknet","start_index":0,"end_index":61}],"logprobs":[]},"sequence_number":7}

event: response.output_item.done
data: {"type":"response.output_item.done","output_index":0,"item":{"id":"msg_1","type":"message","role":"assistant","status":"completed","content":[…]},"sequence_number":8}

event: response.completed
data: {"type":"response.completed","response":{"id":"resp_9f2b","status":"completed","metadata":{"oan_trace_id":"trc_9f2b7c1a","oan_status":"answered"}},"sequence_number":9}
```

**Ten events for one sentence.** `logprobs` is required on both `output_text.delta` and
`output_text.done` — send `[]`. `sequence_number` must be monotonic with no gaps.

**The loss.** The native API sends a sentence and its `source_id` in one frame. Here they are
two events joined by character offsets, so a client drawing live must hold the text until the
annotation arrives.

### 4.4 The question is refused

The farmer asks how to make an explosive. Uses the native `refusal` type.

```jsonc
{
  "status": "completed",
  "error":  null,
  "output": [
    {
      "id": "msg_1", "type": "message", "role": "assistant", "status": "completed",
      "content": [
        { "type": "refusal",
          "refusal": "I can only answer agriculture and livestock related questions." }
      ]
    }
  ],
  "metadata": { "oan_trace_id": "trc_4a1f", "oan_status": "rejected",
                "oan_cause": "unsafe_illegal" }
}
```

Streaming: `refusal.delta` then `refusal.done`, in place of the `output_text` events.

**Why `refusal` and not plain text.** It is the one outcome Responses can express in a typed
field, so using it makes `rejected` visible without reading metadata.

**The cost.** `response.output_text` — the SDK shortcut — joins only `output_text` parts and
**skips `refusal` parts**. A client calling `.output_text` on a refusal gets an **empty
string**, and must read `content[0].type` to learn why.

That is the right trade: a blank screen is a bug a client fixes once. The alternative means no
client can detect a refusal at all without OAN-specific code.

**Not both.** A `refusal` part *and* an `output_text` part with the same sentence would suit
both kinds of client, but one that renders every part shows the sentence twice.

**Note for the adapter.** The native API does not stream a rejection — it sends the terminal
event alone. So the adapter receives no stream here and must synthesize `refusal.delta` and
`refusal.done` from one terminal event. See §5.

### 4.7 Part answered, part refused, and a follow-up needed

*"Which soil is best for potato? What is the price of potato and gold?"*

```jsonc
{
  "status": "completed",
  "error":  null,
  "output": [
    {
      "id": "msg_1", "type": "message", "role": "assistant", "status": "completed",
      "content": [
        {
          "type": "output_text",
          "text": "Potato grows best in well-drained sandy loam soil. Keep soil pH between 5.2 and 6.4. I cannot help with gold prices. Which district should I check potato prices for?",
          "annotations": [
            { "type": "url_citation", "url": "https://icar.example/...",
              "title": "ICAR Potato Guide", "start_index": 0,  "end_index": 49 },
            { "type": "url_citation", "url": "https://icar.example/...",
              "title": "ICAR Potato Guide", "start_index": 50, "end_index": 83 }
          ],
          "logprobs": []
        }
      ]
    }
  ],
  "metadata": { "oan_trace_id": "trc_5b8d", "oan_status": "answered" }
}
```

Two cited sentences carry annotations; the refusal and the question do not. `oan_status` is
`answered` because something was answered.

**Note the refusal is plain text here, not a `refusal` part.** A partial refusal is one
sentence inside an answer — it cannot be a separate content part without splitting the answer
into pieces a client would render out of order. Only a whole-turn rejection uses the `refusal`
type.

**This case works well.**

### 4.8 A voice turn

Same question as §4.1, `oan_channel: "voice"`. The DSS writes differently.

```jsonc
"metadata": { "oan_channel": "voice", "oan_target_lang": "hi", "oan_max_chars": "300", … }
```

```jsonc
{
  "status": "completed",
  "output": [
    {
      "id": "msg_1", "type": "message", "role": "assistant", "status": "completed",
      "content": [
        { "type": "output_text",
          "text": "आनंद मंडी में गेहूं का भाव दो हज़ार दो सौ पचहत्तर रुपये प्रति क्विंटल है।",

      ]
    }
  ],
  "metadata": { "oan_trace_id": "trc_f41c", "oan_status": "answered" }
}
```

Amount spelled out, shorter sentence, **no annotations** — citation markers are not spoken.
The source still went to the audit sink.

Nothing in the Responses format carries the channel. It travels only in `metadata`, and the
difference shows up in the words.

### 4.9 Something broke

```jsonc
{
  "status": "failed",
  "error": {
    "code":    "server_error",
    "message": "A data provider is unavailable. Please try again later."
  },
  "output": [],
  "metadata": { "oan_trace_id": "trc_7c3e", "oan_status": "error",
                "oan_cause": "provider_unavailable" }
}
```

`failed` is correct and an SDK raises on it. But `error.code` must be `server_error` — the
spec's enum has no `provider_unavailable`, no `timeout`, no `domain_unmapped`. The real code
goes in `metadata.oan_cause`.

Streaming: `response.failed` in place of `response.completed`.

**Concurrency cap** returns HTTP `429` with `Retry-After`, before any response object exists.
OpenAI clients retry `429` with backoff by default, so this behaves as they expect.

**Stream drops mid-turn.** No terminal event arrives. The client sees a truncated stream and
must recover by re-issuing with the same `oan_session_id` — the same rule as the native API.
There is no `Last-Event-ID` replay.

### 4.10 The caller sends `store: true`

```jsonc
{
  "error": {
    "type":    "invalid_request_error",
    "code":    "unsupported_parameter",
    "param":   "store",
    "message": "The DSS does not store responses. Set store to false and send history in input."
  }
}
```

`400`. Same for `previous_response_id`.

**The sharpest edge for an SDK user.** `store: true` is the default in several SDKs, and
multi-turn helpers reach for `previous_response_id` on their own. A client following normal
OpenAI patterns hits this on their second turn.

### 4.11 A photo of a diseased crop

An image is a content part beside the text.

```jsonc
{
  "model": "oan-dss",
  "input": [
    {
      "role": "user",
      "content": [
        { "type": "input_text",  "text": "What is wrong with my crop?" },
        { "type": "input_image",
          "file_id": "file_7b2f9c",     // see §6.3 — a URL is not accepted
          "detail":  "auto" }
      ]
    }
  ],
  "stream": false,
  "store":  false,
  "metadata": { "oan_channel": "whatsapp", "oan_target_lang": "hi", … }
}
```

**Response** — an ordinary answer.

```jsonc
{
  "status": "completed",
  "output": [
    {
      "id": "msg_1", "type": "message", "role": "assistant", "status": "completed",
      "content": [
        { "type": "output_text",
          "text": "आपकी फसल में पत्ती झुलसा रोग के लक्षण दिख रहे हैं।",
          "annotations": [
            { "type": "url_citation", "url": "https://npss.example/...",
              "title": "NPSS", "start_index": 0, "end_index": 50 }
          ],
          "logprobs": [] }
      ]
    }
  ],
  "metadata": { "oan_trace_id": "trc_e91a", "oan_status": "answered" }
}
```

Text and image in one request is neater than the native API's separate multipart endpoint. But
**`image_url` must not be accepted** — see §6.3. Once images arrive only as `file_id`, this
surface needs an upload endpoint too, and the advantage over multipart mostly disappears.

**Does not help bharat.** bharat's image flow also holds the answer back instead of streaming
it, and resumes a stalled turn using markers in the history. Neither is about how the image
arrives. So the one deployment with images gains nothing here.

### 4.12 Rejected inputs

| Input | Result |
|---|---|
| `store: true` | `400`, `param: "store"` |
| `previous_response_id` | `400` |
| `input` with `role: "system"` or `"developer"` | `400`, `param: "input"` — see §6.2 |
| `input_image` with `image_url` | `400`, `param: "input"` — see §6.3 |
| `oan_target_lang` not in the supported set | `422` |
| `oan_ref_expires` in the past | Treated as no `ref` at all, per the native API. Not an error. |
| `metadata` over 16 keys, or a value over 512 chars | `400` |
| `input` over the size cap | `413` |

## 5. What the adapter has to do

§4 describes the surface. This is the work of translating to it. **It is not small.**

### 5.1 Five DSS events become fourteen

| DSS native | Responses |
|---|---|
| *(stream opens)* | `response.created`, `.in_progress`, `output_item.added`, `content_part.added` |
| `claim` | `output_text.delta` + `output_text.annotation.added` |
| `turn.completed` | `output_text.done`, `content_part.done`, `output_item.done`, `response.completed` |
| `turn.rejected` | `refusal.delta`, `refusal.done`, `response.completed` — **synthesized**; the native API sends no stream for a rejection |
| `turn.error` | `response.failed` |

### 5.2 Character offsets — the decision that must not be got wrong

`url_citation` needs `start_index` and `end_index` **into the assembled text**. The DSS sends
a sentence plus a `source_id`. So the adapter keeps a running character count, computes each
sentence's span, and emits the annotation after the delta.

The spec says "the index of the first character" and does not say what a character is. For
`"इस सप्ताह आनंद मंडी में गेहूं का भाव ₹2,275 प्रति क्विंटल है।"`:

| Unit | Length |
|---|--:|
| Unicode code points | **61** |
| UTF-16 code units | 61 |
| UTF-8 bytes | 151 |

Runtimes disagree by default: JavaScript strings are UTF-16, Python strings are code points,
Go strings are bytes, Java is UTF-16.

**Decision: Unicode code points.** OpenAI's own SDKs are Python and JavaScript, and for text
in the Basic Multilingual Plane — which covers Devanagari, Gujarati, and Marathi — code points
and UTF-16 units are the same number. Bytes are the wrong answer and are what a naive Go
implementation would produce.

Get this wrong and every citation lands on the wrong words, in exactly the languages this
system serves. It is the most likely bug in a real implementation.

### 5.3 Also the adapter's job

- **`sequence_number`** — monotonic, gapless, per stream. The adapter owns the counter.
- **Echoing required fields** — the eleven constants in §4.1 on every response.
- **Buffering** — spans cannot be computed without holding the text so far.

So: three counters and a synthesis step, per stream. That is state, and where bugs live.

## 6. Security

The native API has none of these problems, because it is only reachable from inside the
subnet. A Responses surface may not be.

### 6.1 `subject_ref` must not be echoed back

The native API treats `ref` as a secret: transported, never inspected, resolved, persisted, or
logged. The design makes it a `SecretStr` so it cannot be printed by accident.

`metadata` is the opposite — designed to be echoed back, and logged freely by SDKs, proxies,
and observability tools.

**Rule: the response echoes only `oan_trace_id`, `oan_status`, and `oan_cause`.**
`oan_subject_ref`, `oan_ref_issuer`, `oan_ref_expires`, `oan_user_id`, and every location key
are dropped on the way out. The adapter must strip them, not rely on the DSS to.

### 6.2 `system` and `developer` roles are rejected

`EasyInputMessage` allows four roles. Accepting `system` or `developer` in `input` would let a
caller override the DSS persona and safety instructions from outside.

`instructions` is ignored for the same reason. That is a security property, not a convenience.

### 6.3 `image_url` is not accepted — SSRF

An arbitrary URL in `input_image` makes the DSS fetch whatever the caller names. That includes
`http://169.254.169.254/latest/meta-data/` for cloud credentials, and any address inside the
private subnet.

**Images arrive only as `file_id`, from an upload the deployment controls.** `data:` URLs are
an option but push whole images through `metadata`-adjacent JSON, so they need their own size
cap.

This is a real regression versus the native API, whose multipart upload carries the bytes in
the request and cannot be pointed anywhere.

### 6.4 `input` is capped

`input` as a message list has no length limit in the spec. The adapter caps total size and
returns `413`. The native API does not need this because its callers are our own services.

## 7. What this surface costs

**Works well**

- Sources are native, with spans.
- Refusals are native and typed.
- History works; the spec supports stateless multi-turn directly.
- Text and image in one request.

**Lost**

- **Two of five outcomes are invisible.** `no_match` and `needs_clarification` look exactly
  like an answer (§4.5, §4.6). Only `metadata` distinguishes them, and no SDK reads it.
- **A refusal returns an empty `.output_text`** for a client that does not check the content
  type (§4.4).
- **Reason codes are gone.** `error.code` cannot hold ours.
- **Location degrades.** GeoJSON becomes a `"lon,lat"` string. A polygon cannot travel.
- **Sentence boundaries blur.** Text and citation are separate events joined by offsets.
- **SDK defaults break.** `store` and `previous_response_id` both `400`.
- **Almost no room to grow.** Fourteen of sixteen metadata keys used on day one.
- **The image advantage mostly evaporates** once `image_url` is refused for SSRF (§6.3).

**Also**

- **`usage` is `null`.** The DSS does not count tokens. A client dashboard will show zero for
  every call.
- **The adapter is not small** (§5). Three counters, a synthesis step, and a decision about
  character encoding that would corrupt every citation if got wrong.

**Unchanged**

The DSS still writes for the channel, still moderates, still cites. Nothing inside changes.

---

## 8. Recommendation

**Do not build this now. Use plain SSE with the DSS-native format.**

One reason above all: **nobody outside our own subnet calls this API.** The DSS is called by
our chat service and our voice service. There is no UI team, no third party, no SDK on this
boundary. A compatible format solves a problem that does not exist here.

The rest supports it. Two of five outcomes stay invisible whatever we do. The adapter carries
real state and one encoding decision that silently corrupts citations in Indian languages if
got wrong. And the format's one genuine advantage — image input in the same request — becomes
an SSRF hole unless it is restricted, at which point it is no better than multipart.

**If it is ever built, it goes in front of the DSS, not inside it:**

```
SDK client ──> Responses adapter ──> DSS (native API) ──> answer
```

The DSS API stays clean, and a second format later is a second adapter rather than a second
contract. The adapter belongs with the channel service, which the OAN architecture already
allows.

**Worth stealing regardless:** the native API's image endpoint could accept an image inline in
the JSON body instead of multipart. That is the good idea here, and it does not need this
surface.

---

## 9. Open

- **`oan_geo` precision.** A `"lon,lat"` string is lossy. Whether polygons are needed is
  unknown.
- **Whether to accept `data:` image URLs**, and at what size cap (§6.3).
- **Which `no_match` behaviour is least surprising.** `completed` is honest but invisible.
  `incomplete` would be visible but is a misuse — `incomplete_details.reason` allows only
  `max_output_tokens` and `content_filter`.
- **Whether the adapter emits `x-ratelimit-*` headers.** OpenAI clients read them.
- **Which OpenAI API version this pins to.** Checked against August 2026. The spec changes;
  `annotations` and the streaming events are recent additions.

## 10. Decisions

| Decision | Choice |
|---|---|
| Adopt this surface? | **No, not now.** No caller exists outside our subnet (§8) |
| Where it would live | An adapter in front of the DSS (§8) |
| Sources | Native `annotations` (§1) |
| **Character offsets** | **Unicode code points.** Not bytes. (§5.2) |
| Refusals (whole turn) | Native `refusal` type. Costs an empty `.output_text`. (§4.4) |
| Refusals (part of an answer) | Plain text in the answer (§4.7) |
| History | `input` as a message list. `user` and `assistant` only. (§3, §6.2) |
| Images | **`file_id` only. `image_url` refused — SSRF.** (§6.3) |
| Response metadata | `oan_trace_id`, `oan_status`, `oan_cause` only. Identity and location are stripped. (§6.1) |
| Request metadata | 14 keys of 16. `subject_ref` flattens into four. (§3) |
| Required response fields | All fourteen echoed, including ones ignored on input (§4.1) |
| `response_max_chars` | `metadata.oan_max_chars`, not `max_output_tokens` (§3) |
| `usage` | `null`. The DSS does not count tokens. (§7) |
| Statefulness | Not supported. `store: true` and `previous_response_id` both `400` (§4.10) |
| Get / cancel / delete | `404` (§2) |
| `no_match`, `needs_clarification` | `completed` plus `metadata`. Known loss. (§5) |
